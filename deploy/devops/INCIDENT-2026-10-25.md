# 2026-10-25: production resource exhaustion

## Impact and recovery

Nest's HTTPS and SSH became unresponsive on the 2 GiB / 1 vCPU production VPS.
Docker's first recorded health-check-start timeout was at 16:45 UTC. The owner
requested a VPS reboot, accepted by Linode at 17:00:22 UTC. The host booted at
17:03:19 and external Nest/engine health and home checks passed by 17:04:54.
The demo `/demo/kibrit-software-factory` exists and its anonymous browser request
correctly redirects to sign-in with the return destination retained.

Both containers restarted automatically with their previous image. Engine/product
database files, runner identity, Codex authentication file and demo files remained
on their existing volumes. The engine reported its original runner online and ten
agents RUNNING, including a fresh NestSystem heartbeat. These are operational and
persistence checks, not a new LLM turn or a claim that every in-flight command was
completed. Bounded read-only SQLite `quick_check` returned `ok` for both databases. Human
sessions expire on process restart as documented.

## Evidence

Persisted sysstat samples from the previous boot:

| UTC | Available RAM (KiB) | Swap used | 1-minute load | Runnable tasks |
|---|---:|---:|---:|---:|
| 16:40:05 | 1,138,828 | 83.99% | 0.61 | 1 |
| 16:50:55 | 65,036 | 99.98% | 62.22 | 59 |

The host has one CPU. At 16:50, kernel CPU accounted for 59.62% of the sampled
interval. Docker could not start health-check processes at 16:45, 16:47, 16:51
and 16:55. HTTPS stalled during TLS and SSH during banner exchange. The previous
kernel journal contains no OOM-kill record; this was observed host starvation,
not a demonstrated kernel OOM kill or an application-only crash.

A syntax-only review of runtime audit records found actual agent build execution
at 16:43:56 and browser/chat validation at 16:44:22, immediately before Docker
began failing. This is the leading trigger supported by the timeline. There is
no retained per-process peak-memory trace proving the exact allocation or process
responsible. Tool calls that merely mentioned test names were excluded.

No deployment was running: the latest completed deployment preceded the incident
by two days. Production's Nest container had no memory, swap, CPU or PID ceiling.
All APIs, agent execution and developer/browser workloads shared that container.
Docker's restart policy handles process exit and daemon startup; it does not
restart a still-running but unhealthy container. Adding more Vitest worker flags
alone would not address this: the container already reports one available CPU.

## Live mitigation

After recovery and explicit owner authorization, an additional 1.5 GiB swap file
was activated alongside the existing approximately 496 MiB swap partition. Total
swap is approximately 2 GiB. The file is root-owned mode 0600, its fstab entry is
persistent, and the previous fstab was backed up. Existing swap was never disabled
and Nest stayed healthy. No container budget, watchdog or new application image
was installed during this mitigation.

Swap is a burst buffer, not replacement RAM. A 2 GiB host should not run full
browser/build validation alongside a production multi-agent service. Consider a
separate build/agent runner or a larger VPS after reviewing actual demand.

## Prevention in this PR

The deployment template reserves host capacity through configurable Nest memory,
swap, CPU and PID ceilings. Container logs rotate. The optional host watchdog
recovers sustained unhealthy state, respects deployment locking, and rate-limits
restart attempts. Its diagnostic output contains only resource/state metadata.
Production-agent instructions route heavy validation to CI or a separate runner.
A disposable local/CI container proves an actual cgroup OOM stays bounded, restarts
and preserves its synthetic volume data.

These controls need explicit host installation/recreation after review. They do
not isolate the API from agents within the same container or add a distributed
scheduler. Agent workload can still fail or interrupt Nest within its budget;
separate runner/compute capacity remains the stronger availability boundary.

Host-owned Docker image builds and direct root-shell workloads are outside the
Nest container cgroup. They need separately bounded/off-host build capacity; this
PR does not claim to constrain the Docker daemon or arbitrary host commands.
