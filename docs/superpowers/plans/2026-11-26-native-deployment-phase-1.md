# Native Deployment Phase 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Wait for plan approval before execution.

**Goal:** Separate the native host controller from app releases and rehearse a restricted, retry-safe protocol v2 deployment whose automatic rollback cannot discard live writes.

**Architecture:** The existing controller remains the forced-command entrypoint. A v2 adapter validates and records immutable requests in a host-owned ledger before a detached systemd job uses a trusted artifact adapter and the existing installer. The installer stores an independent activation checkpoint so systemd and the host job can distinguish reversible failures from cases where data must be preserved.

**Tech Stack:** Python 3.12 standard library (`unittest`, `sqlite3`, `fcntl`, `tarfile`), Bash, systemd, SQLite, existing Ubuntu 24.04 native-host rehearsal.

**Spec:** [Separate Nest releases from private instance operations](../specs/2026-11-26-instance-deployment-design.md).

## Global Constraints

- Phase 1 covers R1–R4, R7–R9 and the host half of R6. Only native Ubuntu 24.04 Linux x64 has v2 deploy support. No Docker fallback, no arm64 v2 deployment, no new restart or rollback RPC, and no changes to OrgOps.
- Treat acceptance as local unit tests plus a disposable VM using synthetic artifacts, secrets, and agents. Do not run any installer, systemd mutation, or rehearsal on the live host. No production credentials, infrastructure provisioning, commits, pushes, or PR changes without separate approval.
- Phase 2 owns GitHub workflow, route, identity policy enforcement in Actions, and external paging; Phase 3 owns immutable publishing and live attestation verification; Phases 4–5 own publication cleanup and optional System. Lack of a production trust adapter must disable v2 deploy capability. Fixture verification is available only in the test harness, never as a production flag, env override, or SSH field. Keep the current deployed controller untouched.
- The spec's pre-implementation checks remain open: select the isolated route or revisit host-pull; confirm private environment restrictions, pinned token-free verification with real attestations and public metadata access, and independent paging/recovery access. Obtain operator confirmation before starting implementation; do not treat synthetic tests as completing those checks. Do not enable production at the end of Phase 1.
- Keep the existing deployment lock, watchdog marker, pre-download 2 GiB artifact limit and 2 GiB non-root reserve. Set the forward deadline to 1,500 seconds and the total job limit to 1,800 seconds, including cleanup and recovery. Keep the 8 KiB submission cap. Use a distinct v2 forced-command binding and never route a v2 request to the legacy path.

## Review Focus

1. Lost SSH acknowledgement, two simultaneous identical requests, or a crash between saving and scheduling must not result in two activations (Tasks 1 and 4).
2. A digest mismatch, untrusted source, or activated release with unknown ancestry must not execute installer code or stop services (Task 2).
3. A snapshot failure halfway through copying both DBs must not permit a partial pair to restore (Task 3).
4. A reboot between closing ingress and recording the cutoff must not let the runner or Caddy start; a post-cutoff runner write must survive a failed smoke check (Tasks 3 and 5).
5. A worker killed during recovery must not release an unhealthy installation to the watchdog or silently retry it (Tasks 4 and 5).

### Task 1: Protocol, policy, and durable request ledger (R1–R3)

**Files:** `deploy/devops/nest-ops.py`, new `deploy/devops/native_ops_v2.py`, new `deploy/devops/test_native_ops_v2.py`, `deploy/devops/README.md`.

**Interfaces:** `parse_request(payload: bytes, policy: ControllerPolicy) -> DeployRequest`; `Ledger.reserve(request: DeployRequest) -> tuple[StatusRecord, bool]`; `Ledger.status(request_id: str) -> StatusRecord | None`; `handle(command: str, payload: BinaryIO, policy: ControllerPolicy, ledger: Ledger, enqueue: Callable[[str], None]) -> dict`. `enqueue` receives only the host-generated `operation_id`, not untrusted command text.

- [ ] Write `test_protocol_is_bounded`, `test_caller_policy`, and `test_duplicate_or_conflicting_submit`. Assert capabilities report `protocol == 2`, `platform == 'linux-x64'`, `max_job_seconds == 1800` and the three spec features on a configured supported host. Reject unknown commands/fields, duplicate JSON keys, over-8 KiB stdin, invalid UTF-8, a bad `<repository_id>:<run_id>` or caller/workflow mismatch. Assert legacy/internal commands cannot reach the scheduler. Assert two concurrent identical submissions for `100:200` save one immutable request and operation ID; a changed digest conflicts; lookup returns the existing record and never queues a job. Assert status omits actor metadata and internal paths and uses the spec's `not_found` shape.
- [ ] Run `python3 -m unittest discover -s deploy/devops -p 'test_native_ops_v2.py'`; expect failure before the new v2 interface exists.
- [ ] Implement the three commands from the spec, bounded streaming input with a read deadline, and validated root-owned policy (private repo ID, workflow ref, target, publisher and platform). Use host-local `/opt/nest/operations/v2.sqlite`, mode `0600`, SQLite transactions with a unique request ID and durable commit; reserve before enqueue. Keep controller policy in `/etc/nest-ops/` and operator-installed modules in `/usr/local/lib/nest-ops/`, outside the app snapshot and release trees. Scope lookups to the configured caller and target. Expose status via field allowlist, never stderr or exception strings from subprocesses. Disable capabilities and submit until a compatible backend and guards exist. In docs, distinguish current legacy installs from opt-in v2; no authorization changes are made here.
- [ ] Re-run the unit command; expect all protocol/ledger tests to pass. Check `test_nest_ops.py` for unchanged Docker tests and rejection of legacy commands on the v2 binding.

### Task 3: Persist cutoff and verify restoration before releasing the gate (R7–R9)

**Files:** `scripts/install-host.sh`, new `deploy/native/activation.py`, new `deploy/native/activation-guard.conf`, new `deploy/devops/test_native_activation.py`, `deploy/devops/test_nest_watchdog.py`, `docs/SPEC.md`, `deploy/native/README.md`.

**Interfaces:** root-owned checkpoint `/opt/nest/operations/activation.json`, outside restored config, atomically replaced and fsynced. `read_checkpoint(path: Path) -> ActivationCheckpoint | None`; `write_checkpoint(path: Path, checkpoint: ActivationCheckpoint) -> None`; `may_start_live_units(checkpoint: ActivationCheckpoint | None, marker_present: bool, active_release: Path) -> bool`. Checkpoint binds the operation ID, old and new release identities, snapshot reference, and ordered state (`pre_cutoff`, `snapshot_verified`, `cutoff`, `restored`, `verified`, `blocked`). Use systemd `ExecCondition` drop-ins installed by the operator, pointing to the pinned host helper. Keep them outside app unit replacement and rollback. A reversible readiness start of loopback APIs requires a current-boot grant in `/run/nest/` scoped to the checkpoint's operation and release; absence after reboot blocks startup of partly migrated or restored databases.

- [ ] Write `test_start_guard_fails_closed`, `test_partial_snapshot_is_not_restorable`, and `test_fresh_heartbeat`. Assert the existing marker plus missing/malformed or pre-cutoff checkpoint denies live service starts, only a matching durable cutoff or restored pair permits them during the transaction, an offline or stale `online` row is not sufficient, and intentional pause never starts the runner. Assert a one-DB copy is never treated as a two-DB restore and reboot cannot start either API against a partial restore.
- [ ] Run `python3 -m unittest discover -s deploy/devops -p 'test_native_activation.py'`; expect failure before the checkpoint and guard exist.
- [ ] Implement the checkpoint and start guard. Before a v2 mutation, require the guard to have been provisioned and loaded for the runner, ingress, and both APIs on the test host. Checkpoint changes must revoke loopback readiness grants before restoring data. Rollback to a release with older service definitions must not remove the operator-installed drop-ins. With the shared lock held, check and persist the existing watchdog marker before downtime, stop/verify writers, and record a restorable snapshot only after both DBs and matching config/release are verified. Keep ingress closed and the normal runner stopped for API/security checks. Persist the cutoff before starting Caddy or the runner; observe `lastSeenAt` before starting and verify advancing freshness and process health after startup. Preserve runner pause and identity. Run bounded ingress/UI smoke checks after cutoff. Do not resume automatic restore from a `cutoff`, `restored`, or ambiguous checkpoint.
- [ ] On a reversible failure, stop writers, restore and verify the matched pair without reopening live access early, then record the restored identity before restarting old services. Record verified rollback and clear the existing marker only after previous-service readiness passes; otherwise preserve it. Once cutoff is recorded, leave new data in place even if the first start fails; distinguish known-active unhealthy from uncertain recovery. Preserve the watchdog's lock and cooldown. Document offline recovery and no automated downgrade. Do not add a second watchdog marker.
- [ ] Re-run activation/watchdog tests and `bash -n scripts/install-host.sh`; expect pass. Replace the old rehearsal expectation that the marker clears when rollback health fails.

### Task 4: Detached job lifecycle and fail-closed reconciliation (R1–R3, R6, R8)

**Files:** new `deploy/devops/native_ops_job.py`, `deploy/devops/native_ops_v2.py`, `deploy/devops/nest-ops.py`, new `deploy/devops/test_native_ops_job.py`, `deploy/devops/nest-watchdog.py`, `deploy/devops/README.md`.

**Interfaces:** `enqueue(operation_id: str) -> None` schedules a fixed systemd unit/command; `run_job(operation_id: str, deps: JobDependencies) -> None`; `reconcile(operation_id: str, deps: JobDependencies) -> StatusRecord`. Consume Tasks 1–3 interfaces. Inject fixture sources and clocks only through test dependencies. Do not parse raw installer output as an outcome.

- [ ] Write `test_claim_is_one_shot`, `test_interruption_after_reserve`, `test_hard_stop_preserves_gate`, and `test_busy_and_recovery_gate`. Assert a lost response or duplicate unit start cannot claim twice, a stale never-claimed reservation becomes `rejected` without retrying activation, busy returns `rejected/busy`, the forward deadline leaves recovery time, and a killed or ambiguous mutating operation becomes `recovery_required` with the marker intact. Assert known post-cutoff health failure becomes `active_unhealthy` and no snapshot restore runs. Status while an active job holds the lock remains readable.
- [ ] Run `python3 -m unittest discover -s deploy/devops -p 'test_native_ops_job.py'`; expect failure before the detached lifecycle exists.
- [ ] Implement fixed systemd dispatch and atomic job claim before activation. Bind the host-owned operation ID to the unit; cap elapsed time including stop grace and children at 1,800 seconds and stop forward work by 1,500 seconds. Check the shared nonblocking lock and recovery marker before release work. Move through the spec phase/state enums and publish only sanitized fields. Use supervised exit handling and boot reconciliation outside the killed worker; do not depend on Bash traps or automatically reschedule a possibly claimed operation. If the watchdog gets the lock between interruption and reconciliation, it must already see the persisted marker. Reconcile durable terminal results before clearing a marker; a crash in that window may leave the gate set for review but must never rerun the deployment. In Phase 1 verify the host-side failure record survives workflow disconnect; real external notification delivery is Phase 2.
- [ ] Re-run the focused job suite and all deployment units with `python3 -m unittest discover -s deploy/devops -p 'test_*.py'`; expect exit zero. Document exact outcome distinctions, bounded logs, and lookup after a lost acknowledgement.
