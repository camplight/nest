# Separate Nest releases from private instance operations

Status: proposed, pending operator approval. This document describes the reusable design, not any installation's inventory or runbook.

## Intent and scope

Nest is a public product for independent installations. An instance operator must be able to deploy a reviewed release from an authenticated interface even when Nest and its agents are unavailable. Preserve the host's guarded activation, backups, health checks, recovery, and audit trail. Do not change OrgOps, product data ownership, or the existing application topology.

The private instance's primary interface will be a manually dispatched GitHub Actions workflow. System is optional and acts only at a human's request. No public merge, release publication, agent decision, or plain chat message may authorize production deployment. No new dashboard or always-running deployment service is needed.

## Approaches

- **Selected: Actions calls the restricted host controller.** Reuse the existing SSH forced command, background host jobs, and deployment lock. Actions submits a request and reports its outcome; the host owns the transaction even if the caller goes away. This requires an approved private network route or controlled runner egress to the host, but does not require granting shell access or opening SSH to arbitrary hosted runners.
- **Alternative: the host pulls approved requests.** Removes inbound access from Actions, but adds a poller, request storage, and reconciliation after interrupted work. Revisit only if a secure route to the existing controller cannot be established.

## Ownership

| Location | Owns |
| --- | --- |
| Public Nest | Build and release CI, native installer, generic Compose and systemd files, reusable controller implementation and versioned interface, example config, and synthetic tests. Public CI can publish releases but has no instance credentials, network access, or deployment trigger. |
| Private instance repo | Production workflow and release policy, host and provider inventory, domains and branding, SSH routing and trust configuration, backup policy and locations, instance health probes, agent/channel bindings, runbooks, incident and deployment history. Keep secret references rather than secret values. |
| Protected runtime and secret stores | Key material, runtime credentials, databases, workspaces, uploads, and actual backups. The operator provisions the controller and its private configuration separately from the app release. |

Audit tracked files, docs, tests, fixtures, screenshots, and both native and CLI release bundles. Replace installation-specific defaults and tests with neutral examples. A generic probe may accept validated instance inputs; public tooling must not embed a particular instance's demo, allowlisted agent, or channel. Keep publisher attribution, project URLs, and upstream references that are not operational settings. Demonstrate a usable independent installation without the private repo. Move real runbooks and incident records without creating a private fork that perpetuates mixed ownership.

The cleanup of current files is distinct from past exposure. Inventory old commits, tags, published bundles, and CI artifacts privately. Revoke or rotate exposed credentials and review exposed access paths. Keep public history intact by default; artifact removals or history rewrites require a separate decision and cannot recall clones or copies. Preserve needed history privately without copying secret values.

## Request, approval, and audit

- A human with production-deployer permission selects a full Nest commit SHA and dispatches the protected workflow. The SHA resolves to one eligible native artifact under the release trust rules below. Private policy can further restrict eligibility. Never compare an approved release to the moving `main` tip, reinterpret `latest` at execution time, or substitute another build.
- The authenticated dispatch for an exact release is the approval; routine deploys do not require a second click by the same person. Production jobs run only from the protected private workflow revision with restricted permissions. Check deployer membership from trusted GitHub identity or enforce it via repo access if all users who can dispatch are operators; do not take an actor or authorization assertion from workflow inputs. Release the deploy credential only to that job and protected ref, using an environment with permitted deployment branches or equivalent enforcement; a broadly readable repository Actions secret is not sufficient. Pin external Actions dependencies. No PR job, public build, or agent gets the host deploy credential. Where a platform feature cannot enforce the desired access rule, fail closed rather than silently weakening it.
- Use a dedicated production-scoped SSH identity and pinned host key. Limit it to the controller's validated operations and safe status; no shell, forwarding, arbitrary commands, file paths, script hooks, or URLs from callers. Treat the protected workflow as the authenticated caller; it passes human and run metadata from trusted GitHub context. Before submitting a mutation, query a read-only capabilities response over pinned SSH. Require the configured controller protocol version and support for verification by digest, durable request deduplication, and safe status lookup. An unknown, missing, or legacy response aborts the run; there is no fallback to `deploy <SHA>`. The host uses a distinct versioned mutation command and disables the legacy mutation interface at cutover. A regular Nest release must stop reinstalling the controller; controller code and policy upgrades are separate, reviewed operator actions. Approved application artifacts remain trusted code: this separation is not a sandbox for a hostile upstream release.
- Correlate the private workflow run ID with the host operation ID. The host record is authoritative for actual state and survives loss of the runner connection. Keep durable, access-controlled records of actor, target, revision/digest, timestamps, stage and outcome, health/rollback result, and an opaque backup reference. Only sanitized summaries leave the host; raw logs, paths, credentials and user data do not enter Actions output or chat. Agree private retention and keep audit history beyond workflow log expiry.
- Deduplicate by request ID: a retry or Actions rerun can retrieve or reconcile the existing operation, not authorize another one. A fresh dispatch is required for a new attempt. A canceled/timed-out workflow is not proof of a canceled host job. Allow status lookup by request ID even if SSH disconnected before returning a host operation ID. Keep the host lock as the final guard against overlapping mutations.

## Release trust

Use GitHub immutable releases for new `native-<full SHA>` tags in the public Nest repository, with one Linux x64 bundle per SHA. Only the public native publish job on protected `main`, after fresh-host checks pass, attests the bundle using GitHub Artifact Attestations (Sigstore-backed SLSA build provenance). Do not republish under the same tag. Check the existing CLI release workflow's edit/clobber-on-rerun behavior before enabling repository-wide immutability; adjust it to treat already published immutable releases as unchanged.

Both Actions and the host use an independently installed, pinned GitHub CLI version. Verify the GitHub release attestation for the asset and verify the artifact's build attestation against GitHub's public Sigstore trust roots. Require the configured public repository, exact native publisher workflow identity, `refs/heads/main`, full source commit, and the GitHub-hosted signer. The request binds the target, repository, exact release tag, approved asset name, and SHA-256 digest. The host independently verifies those inputs against root-owned publisher policy, downloads only from the configured release source, and checks the local bundle digest and expected revision/platform before executing anything from it. A checksum sidecar alone, missing provenance, or mismatched identity fails closed.

## Activation, health, and recovery

1. Acquire the deployment lock before mutation. Check disk headroom before downloading or extracting the artifact, verify integrity before running the installer, and preserve existing preflight/downtime protections. Quiesce writers and capture a coherent snapshot of both SQLite databases and matching release/configuration before migration. Preserve runner identity, the intentional runner pause, workspace/upload state, runtime credentials and compatibility links. Maintain separately encrypted off-host backups of full persistent state, including engine payload files, and rehearse restores in isolation.
2. Reuse the native installer without building on the live host. Run blocking readiness checks for APIs and configured access/security invariants. Persist a rollback cutoff before reopening ingress or enabling real runner work, whichever comes first. Check runner registration before the cutoff only if it can register without consuming real work; otherwise check immediately after. Do not claim runner health on a paused release or infer working external authentication from a config check alone. Run bounded post-open ingress/UI checks as part of the host job and record their results separately.
3. Report `rejected` when no activation was attempted; `succeeded` when activation and required checks pass; `rolled_back` when a failure before the cutoff was followed by a verified restore of the matching databases/configuration/release; and `recovery_required` when rollback fails or host state is ambiguous. Block further routine mutations while that recovery state is unresolved. After the cutoff, a failed smoke check with a known active release is `active_unhealthy`: leave the release and data in place. Only `succeeded` is a successful Actions result. The host records and alerts the operator independently of the workflow connection on `active_unhealthy` or `recovery_required`. A lost connection alone is not a host outcome. A fix-forward is a new authorized request, not an automatic rerun.
4. In v1, post-open rollback is an operator runbook, not a workflow option. Under the host lock, routine deployment requires the active commit to be an ancestor of the requested commit on trusted release history. An exact match is a non-mutating status check. Reject older or unrelated targets and fail closed when ancestry cannot be established. Never infer rollback compatibility from an earlier successful deployment. The operator must establish compatibility on an isolated copy of both current databases and their associated persistent state against the exact target release. If compatibility is unknown, stop for operator-led recovery. If a snapshot restore is necessary, quiesce writers, back up current state, explicitly approve the recovery point and potential write loss, and verify the restored pair. Keep an independent operator host/console path for recovery when GitHub, the network, or the host is unavailable.

## Optional System shortcut

First deliver and rehearse the direct GitHub path. Initially System may help identify the exact release, send the operator to the workflow, and report only authorized, sanitized status. Defer agent execution until it can initiate the same workflow with verified, scoped human authorization tied to a specific release and environment. Do not provision a second path if this cannot be verified independently of the model. If asked for `latest`, resolve it and obtain that authorization for the resolved release. System never holds the deploy key, uses a bot credential as approval, or has a separate mutation path. A quoted, forwarded, injected, or replayed message cannot trigger a deployment.

## Cutover and acceptance

- Rehearse from a clean fixture with no private input and on a disposable host through the private workflow path. Demonstrate valid deployment with the app/agent stopped; rejection of unauthorized requests, legacy controllers, wrong provenance/revision/digest, and downgrade requests without mutation; lost connection and rerun without duplicate execution; backup refusal before migration; failed activation with successful rollback and with recovery required; and retention of runner pause/identity. Verify post-open smoke failures alert the operator without restoring a database snapshot. Restore a full off-host backup in isolation with outbound agent actions disabled.
- Before cutover, confirm the private repo access model, protected workflow capabilities, host reachability, current recovery access, and current backups with the operator. Verify application upgrades do not replace the independently installed controller or revive stale routes. Reject legacy artifacts in the routine workflow if they do not meet that contract; any use for recovery is handled by the operator runbook.
- At cutover, switch authorizations so Actions is the sole routine mutation caller, disable the legacy agent deploy/restart key and remove any equivalent authorization, and test denial from the old path. Do not leave both paths authorized indefinitely or fall back to restoring autonomous deploy privileges. Keep operator break-glass access throughout. Verify the clean public tree and newly published bundles contain no instance operational data; ensure private historical records remain available to authorized operators.

Exact runner/network setup, repository name, request format, and retention values belong in private planning. The initial design does not provision infrastructure, rotate credentials, rewrite history, or authorize a production change.
