# Separate Nest releases from private instance operations

**Status:** proposed, pending operator approval. This describes the target design, not current production behavior or any instance's inventory.

## Direction and scope

**Private GitHub Actions is the primary deploy interface.** An authorized human dispatches a workflow for an exact release, even when Nest is down. Actions calls the existing restricted SSH host controller; the host owns the job, backups, checks, rollback, and final status. **System** is the optional in-Nest operations agent. It may help only at a human's request and has no independent deploy authority. Public CI publishes releases but cannot deploy them. No new dashboard or change to OrgOps is required.

```text
Human dispatch → capabilities check → submit → detached host job → durable status
Actions reads that status by request_id, even if submit's reply was lost.
```

The host-pull alternative removes inbound SSH from the workflow but adds a poller, request storage, and failure reconciliation. It becomes the design if no route meets the network requirements below; revise this spec before building that alternative.

**First delivery (v1), controller protocol v2:** native Ubuntu 24.04 Linux x64 only. The current controller routes non-native hosts into a Docker branch that builds on-host; Docker hosts are **out of scope for v1, not retired**. Keep generic Compose usable and manage those hosts separately until an operator elects native migration or a separate Docker design. The current controller maps `aarch64` to `arm64`, but [native CI](../../../.github/workflows/native-host.yml) publishes only x64. Native arm64 remains a local/operator rehearsal option, not a supported v1 deployment target. Protocol v2 must reject either unsupported target before mutation, never fall back to a build or to the legacy controller.

| Location | Owns |
| --- | --- |
| Public Nest | Build/release CI, native installer, generic Compose and systemd files, reusable controller and its public protocol, example configuration, synthetic tests. No instance credentials or deploy access. |
| Private instance repo | Production workflow and release policy, host/provider inventory, domains, branding, SSH trust and routing, backup policy and locations, health probe inputs, agent/channel bindings, runbooks, deployment and incident history. Store references, not secret values. |
| Protected runtime and secret stores | Keys, runtime credentials, databases, workspaces, uploads, and backup contents. Operators install controller code, verification tools, and private policy separately from app releases. |

## Pre-implementation checks

1. **Route and isolation.** Compare a dedicated self-hosted runner off the production VPS, a tailnet with a short-lived workflow identity and deploy-only ACL, and a GitHub-hosted larger runner with [static egress IPs](https://docs.github.com/en/actions/concepts/runners/larger-runners). Choose based on available plan/region, cost and maintenance, isolation from PR jobs, narrow and revocable network access, independent operation when Nest is down, and recoverability without GitHub. Prove on a disposable host that only the chosen runner identity or egress can reach the deploy SSH route and that the pinned host key is checked. Do not allowlist the general hosted-runner address ranges. If none works, switch to the host-pull design.
2. **Private repo plan and access.** Confirm that the actual plan and repo support [environments, environment secrets, and deployment branch restrictions](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments), or choose an equivalent protected credential broker before proceeding. Confirm which operators can dispatch, how membership is verified, and who can change the workflow or access policy. Do not assume private-repo required-reviewer rules are available or substitute an unrestricted repo secret.
3. **Host verifier.** The distro `gh` installed by [the current installer](../../../scripts/install-host.sh#L68) is not version-pinned. A clean-config check with `gh` 2.103.2 confirms that the default online `gh attestation verify` and `gh release verify-asset` require GitHub API authentication. The pinned CLI's [source](https://github.com/cli/cli/blob/v2.103.2/pkg/cmd/attestation/verify/verify.go#L243-L253) explicitly disables the auth check for `--bundle`; use local bundle verification with `--custom-trusted-root` on the host, not online `gh`. Before implementation, prove a valid public build attestation verifies on a disposable host with no GitHub credentials and verifier network access disabled; also verify wrong and expired/unusable trust inputs fail. Confirm public asset and ancestry access without host credentials. Do not provision a GitHub API credential on the host; if the test fails, revisit verification rather than falling back to an unverified checksum or a token.
4. **Alerting and recovery access.** Choose an external on-call paging service that delivers SMS or email, reached by a host-side notifier independent of Nest, System, and the Actions connection. Test delivery while Nest is stopped and the workflow disconnected. The operator must also verify independent host/console access, current backup age and restore access, and public repository support for immutable releases and build attestations. Keep concrete account, address, and retention settings private.

## Public protocol v2

**R1 — Capabilities and transport (must).** Use pinned host-key SSH with a dedicated target-scoped key, no shell or forwarding. The forced command recognizes only the three operations below. Requests and replies must be size-bounded; fields are typed and validated. Reject unknown commands, fields, or versions, and arbitrary paths, URLs, and scripts. Respond with one JSON object on stdout and exit zero for a handled request, including a stored failed outcome or `not_found`. Invalid or conflicting input and unauthorized requests exit nonzero with a sanitized error. Do not treat a transport or protocol error as a stored deployment outcome.

| Command | Contract |
| --- | --- |
| `v2 capabilities` | Read-only. Returns `protocol: 2`, `target` (configured environment label), `platform` (`linux-x64` for supported hosts), `max_job_seconds` (1800 in v2), and `features` including `verified_digest`, `durable_dedup`, and `status_by_request_id`. Actions must validate the target, platform, protocol and required features before submit. An unsupported host must not advertise deployment support. Missing, malformed or legacy responses fail closed; there is no `deploy <SHA>` fallback. |
| `v2 submit` | Reads one UTF-8 JSON object on stdin, maximum 8 KiB, with the fields in R2. Replies with the durable status record after accepting or resolving an identical request. This call schedules a detached systemd job; it does not wait for activation. |
| `v2 status <request_id>` | Read-only. Returns the same status record, or `{ "protocol": 2, "request_id": "…", "state": "not_found" }`. `not_found` means no record was accepted for that ID; it is not a deployment outcome. No `latest` alias or raw log command. |

**R2 — Mutation fields and idempotency (must).** The only v2 mutation is `deploy`. A request contains:

| Field | Meaning |
| --- | --- |
| `protocol`, `action`, `target` | Integer `2`, literal `deploy`, and the configured target label. |
| `request_id`, `repository_id`, `run_id` | Decimal strings for the private GitHub repository ID and workflow `github.run_id`; `request_id` is `<repository_id>:<run_id>`. Recompute and check it on the host. **Do not use `run_attempt`** in the ID. |
| `actor`, `actor_id`, `workflow_ref`, `workflow_sha` | Original dispatch actor login and stable ID, workflow ref and exact workflow SHA from trusted GitHub context, not operator inputs. The protected workflow attests to this metadata over its scoped SSH identity; the host checks the configured caller repo, workflow ref, and target. |
| `release` | Object containing `repository` (public `owner/repo`), `commit` (40 lowercase hex), `tag` (`native-<commit>`), `asset` (`nest-host-linux-x64.tar.gz`), and `sha256` (64 lowercase hex). Host policy checks all fields; it supplies the fetch locations. |

Persist the immutable request and host-generated opaque `operation_id` atomically before scheduling work. Identical submissions return the existing record; a different payload for the same ID is a conflict and must not modify it. Reconcile the reservation and detached job across lost replies, process interruptions, or reboot without launching a second activation. A GitHub rerun only looks up the original `run_id`; if it was never accepted, require a new dispatch, not a new authorization via rerun.

**R3 — Status and audit (must).** A stored status record returns `protocol`, `request_id`, `operation_id`, `target`, `release`, `state`, `phase`, `created_at`, and `updated_at`; include optional `reason_code`, `health`, `rollback`, and opaque `backup_ref` when known. Timestamps use RFC 3339 UTC. `phase` is one of `queued`, `preflight`, `snapshot`, `activate`, `post_cutoff_checks`, `rollback`, or `complete`. `health` and `rollback` contain only structured check results, not command output. The host retains the original actor and workflow metadata privately with the outcome. Keep audit history beyond Actions log expiry. Only sanitized summaries leave the host: never raw logs, paths, secrets, or user data.

| State | Meaning |
| --- | --- |
| `queued`, `running` | Accepted and awaiting execution, or executing. Neither implies success. |
| `rejected` | Preflight denied activation; the installed release was not changed. |
| `succeeded` | Required checks passed. An exact active commit **and digest** match may be reported with `reason_code: already_active` after read-only health checks, with no activation. |
| `rolled_back` | Failure before the cutoff; the previous matching state was restored and verified. A failed deploy, even though the service was recovered. |
| `active_unhealthy` | Failure after the cutoff with a known active release. Keep current data; never restore a snapshot automatically. |
| `recovery_required` | Rollback failed, or the active state cannot be established safely. Operator recovery is required. |

## Deployment requirements

**R4 — Separate privileged code from app releases (must).** Today [`native_operation`](../../../deploy/devops/nest-ops.py#L100-L132) fetches/checks out `main` and runs both `SOURCE/deploy/native/storage.py` (before downloading) and `SOURCE/scripts/install-host.sh` as root. Checking the bundle's checksum does not authenticate the checkout copies it runs. In v2 the controller runs installer and storage code **only from a safely staged, verified bundle or an independently pinned, root-owned copy installed by the operator. Never execute either from a Git checkout.** Pre-download headroom checks must use the pinned host copy or controller-owned logic, since the bundle is not yet available. Verify before executing anything from the bundle; stage outside agent-writable paths and validate revision/platform before installer execution. Remove both the [installer's controller replacement](../../../scripts/install-host.sh#L439) and its [rollback restore of the controller](../../../scripts/install-host.sh#L240). App activation and rollback must not change controller code, verifier, credentials, or policy. Separating those updates does not sandbox approved release code.

**R5 — Release trust (must).** Public native CI publishes one immutable `native-<commit>` Linux x64 bundle per SHA. After fresh-VM checks pass, the protected main publish job creates a GitHub Artifact Attestation (Sigstore/SLSA build provenance) over the exact shipped bytes and includes its local bundle in the immutable release. Never replace a published asset or tag. [CLI release CI](../../../.github/workflows/release-main.yml#L146-L160) currently edits releases and uses `upload --clobber`; make reruns leave existing published releases unchanged before enabling repository-wide immutability.

- **Actions** uses its scoped, read-only GitHub API authentication and a pinned CLI to verify the GitHub release attestation for the exact tag and asset and resolve its digest. It also verifies build provenance before submit.
- **The host** downloads the artifact and build-attestation bundle from the configured public release source without an API credential. It verifies the request digest and checks build provenance independently using the operator-installed, pinned `gh`, a local `--bundle`, and a root-owned `--custom-trusted-root` obtained and rotated separately from the app release. Both verifiers require the trusted publisher repository and exact native publish workflow, `refs/heads/main`, the exact source commit, and a GitHub-hosted signer. The host checks the bundle metadata and expected platform; a checksum sidecar, mutable tag, missing signature, or mismatched identity is not enough. Online release-attestation lookup remains in Actions, not on the host.
- Under the deployment lock, require the active commit to be an ancestor of the requested commit in trusted publisher history, or an exact commit/digest match. Use public ancestry metadata or bare history, not a checkout for execution. Refuse older, unrelated, or indeterminate targets. Never reinterpret `latest` at execution time or require equality with the moving `main` tip. Bootstrapping a host or migrating it from Docker remains a separate operator action.

**R6 — Workflow authority and time bounds (must).** A protected manual dispatch by an authorized deployer for an exact SHA is the approval; no second routine click. Check the original human identity and membership from trusted context. Restrict production secrets to the allowed ref and protected workflow, pin external Actions dependencies, and give public CI, PR jobs, and agents no deploy key. Use one workflow `concurrency` group per production host, with `cancel-in-progress: false`. GitHub pending runs are not a durable queue; the host lock is the final guard. If the host job cannot acquire the lock, record `rejected` with `reason_code: busy`, without waiting for another deployment to finish.

- Set 10-second SSH connect and 30-second RPC deadlines, bounded network and service calls, and a 35-minute Actions job deadline. Report a workflow timeout or cancellation as **host outcome unknown** until a status lookup resolves it, not as a canceled host job.
- Limit each detached host job to **30 minutes** including recovery: stop forward progress by minute 25 (or earlier if the next stage does not fit), reserve the remaining time for bounded recovery, and enforce the total using the host supervisor. Rehearse those limits for supported release/state sizes. Reconcile expired or interrupted jobs from durable checkpoints; do not rely on a shell trap after an abrupt kill. If coherence or the cutoff cannot be proved, set `recovery_required`, preserve state, and never auto-restore or start another activation.

**R7 — Backups and cutoff (must).** Check disk headroom before download/extraction and again before downtime. Hold the shared deployment lock, stop live writers, and verify a coherent snapshot of both SQLite databases and matching config/release before migration. Preserve runner identity, pause state, workspaces, uploads, and runtime credentials. Keep encrypted off-host backups of full persistent state, including engine payload files, and rehearse isolated restore with outbound agent work disabled.

- **Required installer change:** it [currently starts the runner](../../../scripts/install-host.sh#L401-L409) and [checks its registration](../../../scripts/install-host.sh#L419-L431) before [starting Caddy and setting `committed=1`](../../../scripts/install-host.sh#L445-L447). The normal runner can accept work in that gap; restoring the old snapshot can discard runner writes. Keep the normal runner stopped and ingress closed through blocking readiness checks. Prevent restart/boot paths from starting either early. Durably record the cutoff **before enabling either live ingress or normal runner work**, whichever comes first. A failure after the cutoff never triggers snapshot restore, even if the first service start failed.
- Before the cutoff, verify loopback API readiness and configured security invariants without real agent work. After it, if not paused, start the normal runner and require `nest-runner` active and a **fresh** authenticated runner registration/heartbeat for the persisted ID (`lastSeenAt` must advance from the pre-start observation and be at/after the new start; a stale `online` row is insufficient). If paused, verify the unit remains stopped; do not claim runner health. Run bounded external ingress/UI smoke checks and record results separately from readiness. Provider configuration checks do not prove live OAuth login.

**R8 — Recovery, watchdog, and alerts (must).** For a reversible pre-cutoff failure, restore the matching DB/config/release pair and verify it before recording `rolled_back`. In `recovery_required` and `active_unhealthy`, keep or set the existing `/var/lib/nest-watchdog/recovery-required` marker before releasing the lock. [`nest-watchdog.py`](../../../deploy/devops/nest-watchdog.py#L85-L100) already checks it under that lock. Use it to block `nest-native-watchdog` restarts for both outcomes, including across reboot. Do not introduce a second marker or let the installer clear this one prematurely (it currently clears it [before rollback health is verified](../../../scripts/install-host.sh#L259-L266) and [before Caddy starts](../../../scripts/install-host.sh#L443-L446)). Check for an existing marker under the lock and reject routine mutations while it remains. Set the marker before beginning the activation transaction so an interrupted job cannot leave the watchdog free to act. Clear it only after verified healthy activation/recovery or explicit operator resolution. Record the result and send a sanitized notification via the external pager for either failure state, even if Actions disconnected. Retry notification on a bounded schedule without retrying deployment. Only `succeeded` is a successful workflow result.

**R9 — Operator-led post-cutoff recovery (must).** No workflow rollback to an older release in v1. A fix-forward requires the operator to resolve the gate and dispatch a new authorized run. For a downgrade, verify compatibility of the exact target on an isolated copy of both current databases and associated state; never infer compatibility from an earlier successful deploy. If a snapshot restore would discard writes or compatibility is unknown, stop for operator-led recovery: quiesce writers, back up current state, explicitly approve the recovery point and potential write loss if restoring, and verify the recovered pair. Keep independent host/console access for GitHub or network outages.

**R10 — Public cleanup (must).** Inventory tracked files, docs, tests, assets, screenshots, and native/CLI release bundles, not only `deploy/`. The current [`health()`](../../../deploy/devops/nest-ops.py#L62-L86) embeds an instance domain and demo, and the [installer's pre-open check](../../../scripts/install-host.sh#L436-L437) embeds a specific demo route. Keep generic checks public and move live probe values and bindings into validated private configuration. Use neutral fixtures and examples; retain product attribution and useful upstream URLs. Move operational data and incident history to the private repo without creating a long-lived private product fork. Separately inventory old commits, tags, downloads, and CI artifacts. Revoke or rotate exposed credentials; do not rewrite public history or remove published artifacts without an explicit decision, and do not imply old copies can be recalled.

**R11 — Optional System shortcut (should, after direct dispatch works).** Start with exact release selection, a workflow link, and authorized sanitized status. If System later submits, it must act only on verified human authorization bound to the same exact release and target and use the same protected workflow. An informal `latest` request needs confirmation after resolution. Quoted, injected, forwarded, or replayed chat cannot authorize deployment. No agent-held deploy key, bot-only approval, or second host mutation path.

## Delivery and acceptance

1. **Separate controller and add protocol v2** (R1–R4, R7–R9). On a disposable x64 host with trusted fixtures, prove install and rollback never replace the controller or run installer/storage code from a checkout. Accept v2 only, reject unsupported targets and malformed requests, and reconcile a lost reply and replay to one operation. Prove backup refusal before migration, verified pre-cutoff restore, stale heartbeat rejection, pause/identity preservation, and preservation of a synthetic runner write when a post-cutoff check fails. Force an interruption and a failed restore; verify that the marker persists across reboot and the watchdog suppresses restarts in both `active_unhealthy` and `recovery_required`.
2. **Private Actions workflow and network path** (R1–R3, R6, R8). Keep production credentials disabled. On the chosen route, show authorized dispatch and host status with Nest/System stopped, rejection of unauthorized actors, unprotected refs and legacy controllers, and denial from outside the allowed route. Exercise concurrency, workflow timeout, lookup-only reruns, host deadline and external pager delivery with the workflow disconnected. No production deployment during this phase.
3. **Immutable releases and attestations** (R4–R5). Fix CLI publication first; repeat publishing without modifying existing releases. On a disposable host, verify a real release with the pinned token-free verifier, and reject wrong digest, signer, source ref, revision, platform, or ancestry before executing any release code. Reject legacy artifacts that would reinstall the controller. Do not enable production until all checks pass with real signed artifacts.
4. **Clean up the public repo** (R10). Treat the inventory and migration as a separate workstream; it can start early. A fresh independent installation must work with no private repo, using synthetic probes, generic docs, and no instance data in the current tree or new release bundles. Confirm private runbooks and audit history are usable.
5. **Optional System shortcut** (R11). After cutover and direct workflow rehearsal, show that a human-authorized shortcut uses the same workflow, audit record, and permissions. Verify that an agent alone or a replayed request cannot deploy, and that the direct workflow still works without System. Defer execution if that authorization cannot be enforced outside the model.

**Documentation gate for each phase:** Update [the product spec](../../SPEC.md), [host-operations README](../../../deploy/devops/README.md), and any affected [native runbook](../../../deploy/native/README.md) and [migration notes](../../SUBMODULE_MIGRATION.md) in the same change as the behavior they describe. They document the current implementation and are not changed by this proposal.

**Production cutover gate (after phases 1–4):** Rehearse the complete signed-release workflow and full off-host restore on a disposable host. Confirm current backups, external paging, and break-glass access with the operator. Switch routine mutation authority to Actions, revoke the legacy agent deploy/restart key and equivalent access, and test that the old path is denied. Keep operator recovery available throughout; do not restore agent mutation privileges as fallback. This proposal does not authorize a deployment, history rewrite, or infrastructure change.
